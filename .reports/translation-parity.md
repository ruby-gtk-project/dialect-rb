# Translation parity — dialect-rb vs upstream `origin/main`

## msgid count

`po/` is a checked-out git submodule (`dialect-app/po`, pinned at
`21a043f` / `2.2.0-252-g21a043f`). `po/ui/dialect.pot` contains:

    grep -c '^msgid' po/ui/dialect.pot
    123

Upstream also ships a second catalog (`dialect-cldr-langs`, generated by
`po/gen_cldr_langs.py` for the language-name strings) and ~35 call sites in
`dialect/window.py` alone wrapped in `_()`.

## Survival: zero

    grep -rn "GetText\|FastGettext\|\.gettext\|_(\"" lib exe
    → no matches

    grep -rn "gettext" lib exe
    → lib/define.rb:30 and lib/languages.rb:23, both comments *about* gettext,
      not calls to it

There is no `bindtextdomain`, no `_()`, no `pgettext`, no gettext gem in the
`Gemfile`, and no `GetText`/`FastGettext` require anywhere in `lib/` or
`exe/`. Every one of the 123 msgids in `po/ui/dialect.pot`, and every string
in the CLDR language catalog, is unreachable at runtime: the catalogs are
present in the tree (`po/` is checked out) but nothing in the Ruby source
reads them. Survival rate: **0 of 123** msgids are live-translatable in the
port, regardless of how many of their English source strings were copied
verbatim into the Ruby literals.

## This is accurately disclosed, not hidden — and that matters for scope, not severity

Both `.reports/component-inventory.md` and the commit that checked out `po/`
(`54b3308`) say this plainly:

> "no gettext integration exists yet, so this is not translation parity" —
> commit message, `54b3308`
>
> "the Ruby source carries no `gettext` integration at all ... That is a
> distinct, much larger unit of work (the `translation-parity` skill's
> remit) that nobody has done; it does not get credited here as part of unit
> 37 being merely checked out." — `component-inventory.md`

This is the right way to report a gap — naming it instead of letting the
"po/ is checked out" milestone imply more than it does — and it is noted
here as a point in the project's favor on `accountability-ensurance.md`. It
does not change the scope of what's missing: a user who sets `LANG=de_DE`
(or any of the ~100+ locales `po/ui/LINGUAS` lists) gets the identical
English-only UI as a user with no translations installed at all. That is a
total, not partial, translation gap.

## What's missing, concretely

1. A gettext binding (`gettext` gem, or `FastGettext`) in the `Gemfile`.
2. `bindtextdomain`/locale setup at startup in `lib/main.rb`, naming the
   `dialect` domain and the checked-out `po/` catalogs' install path.
3. Every user-facing string literal in `lib/*.rb` — window titles, button
   labels, menu items, error messages, the shortcuts dialog, the preferences
   dialog, the About dialog's strings — wrapped in `_()`/`pgettext()`
   equivalents instead of being bare Ruby string literals.
4. A way to generate/update a Ruby-side `.pot` (or reuse the checked-out
   `po/ui/dialect.pot` if the msgids are kept string-identical) so the
   existing translator community's work in `po/` actually applies to the
   Ruby strings it's matched against.
5. The CLDR language-name catalog (`dialect-cldr-langs` domain,
   `po/gen_cldr_langs.py`) wired into `lib/languages.rb`, which currently
   only has a comment noting upstream "additionally runs the name through
   gettext's pgettext" — i.e. the comment documents the gap without closing
   it.

## Verdict

**Not clean.** 0 of 123 msgids are reachable at runtime. This is the single
largest remaining unit of work in the port and should not be understated by
the fact that `po/` itself is present in the tree.
